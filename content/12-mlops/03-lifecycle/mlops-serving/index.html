MLOps & model serving

Regular software has one thing that changes: code. An ML system has three —

Code, data, model — and every difficulty comes from that.

This lesson pins down four deployment strategies with their blast radius, how to detect drift with numbers, four monitoring layers, and the point-in-time correctness problem.

01

Mental model

MLOps answers exactly one question: can someone else rebuild this model, and who notices when it gets worse.

A model's lifecycle is a closed loop, and most ML incidents sit on the connecting arrows, not in the model itself.

Remember one sentence

In an ML system, the model is only a very small part. Most of the effort and most of the incidents are in data, feature infrastructure, deployment and monitoring. Being able to say this is a sign you have run a real system, not just trained models in a notebook.
02

Why ML differs from regular software

Regular software

What changes code

Testing fixed input → fixed output

How it fails throws, crashes, logs a stack trace

Decays over time no — unchanged code means unchanged behavior

Reproducibility same code gives the same result

ML system

What changes code + data + model

Testing output is a distribution; "correct" is a range

How it fails silently gets worse with no error at all

Decays over time yes — the world changes and the model goes stale even with identical code

Reproducibility needs the same data, seed, libraries and hardware too

The two middle rows are the root of every difficulty

A broken API returns a 500 and you know immediately. A broken model still returns 200 with a number that looks plausible but is wrong. No exception, no alert from ordinary systems. That is why ML monitoring must be a separate layer, and why it cannot rely on infrastructure monitoring tools alone.
03

Versioning — four things, not one

Code — Gitobvious
Data — DVC, LakeFS, or timestamped snapshotsif you don't know which data you trained on, you can neither reproduce nor debug
Model — MLflow, W&B, platform registryyou need to know which artifact is running, from which commit, on which data
Feature definitions — feature store or versioned codea feature whose definition changes without retraining the model is a silent form of skew
Environment — Docker, lock filebumping one library version can change results

The question that tests whether a system is mature enough

"Which commit and which data is the production model from, and how long does it take you to rebuild it?" If the answer is not clear and under a day, the system is not mature yet — and when an incident hits, nobody can debug it. Raising this exact question in an interview is the fastest way to show you understand the problem.

six things to record for every training runmiss one cell and you cannot rebuild it

But bit-exact reproduction on GPU is not feasible

The accumulation order in parallel operations is nondeterministic, so two runs with the same config still give weights that differ in the last digits. The practical goal is not bit-for-bit equality but equality within tolerance: a rerun must give metrics within the normal seed-to-seed variation. Knowing this boundary — and knowing how large the seed-to-seed variation is for your own problem — is the mark of someone who has measured.

The practical consequence: if two models differ by 0.3% AUC and seed-to-seed variation is 0.5%, you have not yet shown that either model is better.

Running several seeds and reporting the mean with its standard deviation is the right way.

Shadow is the most valuable gate and the most often skipped

It is the only way to catch training–serving skew before users are affected: the model receives real traffic, computes features through the real serving path, and you compare the prediction distribution with the offline one. If the two distributions diverge, something differs between the two feature paths — and you learn that with 0% risk to users.
06

Packaging and serving

Protocol — REST or gRPCgRPC is faster for internal traffic thanks to binary encoding and HTTP/2; REST is easier to integrate
Model format — native, ONNX, TensorRTONNX for portability; TensorRT for speed on NVIDIA GPUs
Serving server — Triton, TorchServe, or hand-written FastAPIdedicated servers ship with dynamic batching and multi-model management
Dynamic batching — group requests within a small windowlarge throughput gain for a small latency cost — almost always worth it
Autoscaling — on QPS or queue lengthheavy models have long startup times, which must be factored into scaling thresholds

On dynamic batching

The server waits a very short window — say 5ms — to group the requests arriving in that span into one batch. It adds at most 5ms of latency but throughput can rise several-fold, because a GPU processes a batch at nearly the cost of a single sample. This is the same principle as batching in LLM inference: the hardware is bound by reading weights, not by the number of samples.

An operational detail that is often overlooked: startup time.

Large models take tens of seconds to a few minutes to load, so when autoscaling fires the new machines are not ready right away.

You must keep some headroom, use preloading, or alert on trends instead of instantaneous thresholds.

07

Lab: deployment strategies

Pick a strategy and enter a scenario to see how many users are affected before you can detect the problem and roll back.

Compare a 5% canary with a direct 100% rollout: same faulty model, same detection time, yet the number of affected requests differs twentyfold.

Then try cutting detection time from 10 minutes to 1 —

Good monitoring is worth as much as cutting the traffic share.

08

Rollback and fallback paths

1 · Revert to the previous versionthe old model is still in place, just change config — must take minutes, no rebuild
2 · Fall back to a simpler modelsmaller, older, but sure to work
3 · Fall back to rulesstatic logic or default values — the feature degrades but does not die
Rollback must be a config changenot a redeploy — a rebuild costs 20 precious minutes
Never let the model block the main pathput a timeout on model calls; on timeout use a default value instead of leaving the request hanging
Rollback drillsa procedure never rehearsed does not exist — drill it regularly
Keep old models long enoughsome incidents only surface after several days

Graceful degradation

The most important design point: the system must survive when the model dies. A recommendation page can show popular content; a fraud system can fall back to rules; a search box can use plain keyword matching. A degraded feature always beats an error page, and raising this in a design round almost always earns credit.
09

Monitoring layers

1 · Infrastructure — CPU, memory, p99, error and timeout ratescatches technical incidents · instant signal
2 · Data — feature distributions, missing values, out-of-range values, schemacatches dead data sources, format changes, drift · instant signal
3 · Model — prediction score distribution, rate above threshold, performance once labels arrivecatches stale models, feature-path skew · scores are instant, performance waits for labels
4 · Business — revenue, engagement, complaintscatches real impact · slow, noisy signal

Layer 2 is the one most worth investing in

Because it gives an instant signal while true labels may arrive weeks later. And it catches a whole class of incidents no other layer catches: a field renamed at the source, an API returning empty, an ETL job dying silently. These incidents degrade the model immediately while every infrastructure metric stays green. Saying "I monitor feature distributions because labels arrive late" is a very strong answer.

A detail worth adding: monitor by segment, not just overall.

A model can hold its overall performance yet drop sharply on one group —

A region, a device type, a customer segment —

And the average hides that completely.

10

Detecting drift with numbers

Data drift — P(x) changes

The input distribution changes: a new user group behaves differently. Detectable immediately, no labels needed.

Concept drift — P(y|x) changes

The relationship between inputs and labels changes: fraudsters change tactics, so the same features now mean something else.

Only detectable once labels arrive — so always late.

PSI — Population Stability Indexfor numeric or binned features · < 0.1 stable · 0.1–0.25 worth watching · > 0.25 clear drift
KS testfor continuous features · oversensitive on large data, the p-value is always tiny, so look at effect size instead
Chi-squarefor categorical features · same caveat as above
Prediction score distributionfor the whole model · the best aggregate signal, it folds in every input change
PSIdistribution shift = Σ (pnew − pbase)share difference per bin × ln( pnew / pbase )ratio difference

Summed over the feature's bins. Below 0.1 is stable; above 0.25 is clear drift.

A warning about statistical tests for drift

With millions of samples, the KS test reports a "significant difference" for every feature, even completely harmless changes — this is exactly the problem from the Statistics & A/B testing lesson: a large sample size makes every difference statistically significant. So use an effect size such as PSI, and always check by eye by overlaying the two distributions.
11

Retraining — when and with what

Scheduled — daily, weekly, monthlysimplest and predictable — a good default
Drift-based — run the pipeline when PSI crosses a thresholdwhen drift is uneven: quiet at times, spiking at others
Performance-based — metric drops below the baronly usable if labels arrive quickly
Data-volume-based — retrain after N new samplesearly stage, while data is still scarce

Choose the frequency by drift speed, not by habit. Fraud detection faces attackers who adapt constantly, so it may need daily retraining;

Product image classification can go monthly without losing anything.

And every retrain must pass the same gates as in section 05 —

A new model is not automatically better than the old one.

Retrain from scratch or continue training

Retraining from scratch on the most recent data window is simple and predictable, but expensive. Continuing from the old weights is much cheaper, but errors accumulate over rounds and are hard to spot. The common pragmatic approach: continue training often, and periodically retrain from scratch as a reference point and to cut accumulated drift.
12

Feature store and point-in-time correctness

The same feature has to be computed twice, in two different environments — and the two paths easily drift apart without any error.

Training path

SQL on the data warehouse, batch processing, historical data.

Serving path

Python inside the service, one request at a time, live data.

mismatches in missing values, time zones, rounding, event orderthe model mysteriously gets worse, with no error at all

The fix: a single place that defines features and generates both paths.

Point-in-time correctness — the hardest part

A training example's features must be the values at the exact prediction time, not today's values.

Why feature stores exist

Point-in-time correctness is the main reason feature stores exist — not because they are a handy cache. Hand-writing point-in-time joins for dozens of features is very easy to get wrong, and getting it wrong creates time leakage with no visible sign. Understanding this is understanding why a feature store cannot be replaced by a cache.

And you need to know when you do not need a feature store.

If you only have a few simple features, or everything can be computed from the request itself, adding another system is not worth the cost.

It starts paying off when many models share features, or when you have many time-window aggregate features.

13

Maturity levels

0 — manualtrain in a notebook, hand the model over manually
1 — automated pipelineruns with one command; has a registry and monitoring
2 — CI/CD for the pipelinethe pipeline itself is tested and deployed automatically

nobody can rebuild the running modelretraining is routineidea to production in a few hours

Which level is enough

Level 1 is enough for most organizations, and pushing to level 2 too early is a form of over-engineering — you build infrastructure for a retraining frequency you do not need yet. A strong interview answer states which level you are at, why that level fits the problem, and what the next step will be and when — instead of listing every MLOps tool.
14

Common mistakes

Not versioning data

Cannot reproduce, cannot debug. Timestamped snapshots are the bare minimum.

Skipping the shadow step

You lose the only chance to catch training–serving skew at 0% risk.

Rollback that needs a rebuild

Tens of minutes lost in the middle of an incident. Rollback must be a config change.

Monitoring only infrastructure

A broken model still returns 200 with a plausible-looking number. You need a data monitoring layer.

Using the KS test p-value to flag drift

On large data every feature is "significant". Use an effect size such as PSI.

Point-in-time-incorrect feature joins

Time leakage. The model looks good in testing, useless in production.
