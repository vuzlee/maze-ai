Transaction & isolation

Group writes so they all happen, or none do.

  • BEGIN … COMMIT wraps a transaction
  • ACID: atomic, consistent, isolated, durable
  • isolation level trades safety for speed
01

Mental model

Either every step commits, or the database rolls back to where it started.

BEGIN; UPDATE accounts SET bal = bal - 100 WHERE id = 1; UPDATE accounts SET bal = bal + 100 WHERE id = 2; COMMIT;

02

ACID

Four guarantees every transaction gives.

2.1Atomicity

All or nothing.

2.2Consistency

Constraints hold before and after.

2.3Isolation

Transactions don't see each other's unfinished work.

2.4Durability

After COMMIT, data survives a crash.

03

Read anomalies

What can go wrong when transactions run at the same time.

3.1Dirty read

Reading uncommitted data.

3.2Non-repeatable read

The same row changes between two reads.

3.3Phantom read

The same query returns new rows.

04

Isolation levels

Each level blocks one more anomaly.

Defaults: PostgreSQL read committed, MySQL repeatable read. SET TRANSACTION ISOLATION LEVEL SERIALIZABLE

05

Locks

How concurrent writes take turns.

5.1Row lock

A write locks the row until commit.

SELECT … FOR UPDATE takes the lock while reading.

5.2Deadlock

Two transactions wait on each other; one is aborted.

  • Avoid it: touch rows in the same order, keep transactions short.
