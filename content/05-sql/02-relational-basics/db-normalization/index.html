Normalization & denormalization

Store each fact in exactly one place.

  • repeated data goes out of sync — anomalies
  • fix: split the table and link with keys
  • denormalize only when reads must be faster
01

Anomalies

When a fact is stored twice, one copy will eventually be wrong.

1.1Update anomaly

Change one copy, forget the other.

1.2Insert anomaly

Cannot add a fact without an unrelated one.

1.3Delete anomaly

Deleting one fact loses another.

02

Normalization

Split tables until each fact lives in one place.

2.1Splitting tables

Move each repeated fact into its own table and point to it with a foreign key.

2.21NF

One cell holds one value.

2.32NF

Every column depends on the whole key, not part of it.

2.43NF

Non-key columns depend only on the key, not on each other.

3NF is the usual target for application databases.

03

Denormalization

Copy data back on purpose when reads matter more than writes.

  • Normalized: one place to update, JOINs on read — OLTP.
  • Denormalized: fewer JOINs, many copies to sync — reports, dashboards.
