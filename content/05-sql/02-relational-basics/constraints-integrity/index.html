Constraints & integrity

Declare the rules once in the table, and the database rejects every bad row.

  • a constraint is a rule attached to a column or a table
  • integrity means the data is correct — constraints are how you keep it
  • a bad write is rejected and the table stays unchanged
01

Mental model

A constraint is a gate in front of the table: valid rows go in, bad rows are sent back.

  • Checking in the database covers every write path: the app, manual scripts, background jobs.
  • Keep checks in the app too — they give users friendlier error messages.
02

Constraints

Six rules you declare on columns.

2.1PRIMARY KEY

Unique and never NULL; one per table.

id INT PRIMARY KEY

2.2FOREIGN KEY

Must point to a row that exists.

customer_id INT REFERENCES customers(id)

2.3NOT NULL

Blocks missing values.

email TEXT NOT NULL

2.4UNIQUE

Blocks duplicates; NULLs are still allowed.

email TEXT UNIQUE

2.5CHECK

Blocks values that fail a condition on one row.

age INT CHECK (age >= 0)

2.6DEFAULT

Fills a value when none is given — blocks nothing.

status TEXT DEFAULT 'draft'

03

Types of integrity

Three kinds of correctness the constraints protect.

3.1Entity integrity

Every row can be identified.

Enforced by PRIMARY KEY.

3.2Referential integrity

Every reference points to something real.

Enforced by FOREIGN KEY.

3.3Domain integrity

Every value is valid for its column.

Enforced by types, NOT NULL, CHECK, DEFAULT, UNIQUE.

04

ON DELETE

When a parent row is deleted, what happens to the child rows pointing to it — choose by business rule.

4.1RESTRICT

Block the delete while children exist — the default.

ON DELETE RESTRICT (or NO ACTION) — customers who have orders.

4.2CASCADE

Delete the children with the parent.

ON DELETE CASCADE — order_items of an order.

4.3SET NULL

Keep the children, clear their key.

ON DELETE SET NULL — an employee whose manager leaves.
