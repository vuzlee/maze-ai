NoSQL & data systems — overview

Read this first. It answers three questions: what you gain by dropping relational tables, which path analytical data takes, and what order to learn in.

01

Mental model

The SQL shelf optimizes for one job: many people editing a few rows at once, with absolute correctness. This shelf covers two quite different jobs — data that does not fit the table mold, and scanning billions of rows to answer one question.

  • Read this shelf after the SQL shelf, not instead of it: every choice here only makes sense once you know what you are giving up — constraints, JOIN, transactions.
  • The name "NoSQL" is misleading. It does not mean "no SQL" — many systems in the group still have an SQL-like language. It means not using the relational model.
02

Which lesson for which problem

A reverse lookup: which symptom you have, which lesson to read.

NoSQL — four familiesEvery record has a different shape · the schema changes constantly · you only ever look up by one key · what you need to query is the relationships between entities.
OLTP vs OLAPOne reporting query slows down the whole customer-facing system · you want to know why analytics systems store data by column.
Data systemsData is spread across many systems and none can answer the overall question · rerunning the pipeline doubles the numbers · daily results are too slow · reports are wrong and nobody knows the data broke.
  • For ML practitioners, that lesson's data quality and batch vs stream sections touch daily work the most: training features and serving features must be computed the same way.
  • Data systems is one continuous pipeline, not four separate topics: where to store → how to move → on what cadence → are the numbers right.
