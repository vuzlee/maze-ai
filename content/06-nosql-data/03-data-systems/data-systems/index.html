Data systems

Data travels from where the application writes it to where analysts read it. Four things to remember:

  • where to store it — a warehouse enforces schema up front, a lake at read time
  • how to move it — ETL or ELT; a rerun must give the same result
  • what cadence — batch or stream, chosen by the business's latency needs
  • are the numbers right — a green pipeline does not mean correct data
01

When to pay the cost

Both must clean data and enforce a schema — the difference is whether that cost is paid before storing or when someone reads.

  • A warehouse is schema-on-write: enforced up front, so reading is just running SQL.
  • A lake is schema-on-read: dump data as-is into cheap storage, work out the structure later.
  • A warehouse requires knowing your questions in advance; a lake lets you defer, but readers must figure things out themselves.
  • Most companies have both — data without a clear purpose stays in the lake; once the questions settle, it moves into the warehouse.
02

Star schema

The standard shape of a warehouse: one fact table in the middle, with dimension tables around it as axes for slicing.

  • The fact table holds keys and measured numbers; dimensions hold everything descriptive.
  • Only one level of JOIN, so aggregation is very fast — that is why this shape exists.
  • This is the deliberate denormalization of OLAP, not a standard that replaces 3NF.
  • A snowflake schema splits dimensions into several levels: less duplication, at the cost of more JOINs.
03

Raw, cleaned and mart layers

In both warehouses and lakes, data is usually arranged in three layers — each a level of cleanliness, not a redundant copy.

  • raw stays as-is so you can rebuild when a pipeline computes something wrong.
  • cleaned is the shared table every team reads — so two teams' numbers never diverge.
  • mart is pre-aggregated per team's needs; adding one does not touch running pipelines.
  • Drop the middle layer and every team defines "revenue" its own way.
04

Where to put Transform

The three steps are fixed — the only question is whether Transform comes before or after Load, and that choice follows the target store.

  • ETL transforms in a separate engine and only then writes the clean version to the warehouse.
  • ELT loads near-raw data into the store, then transforms it in place with SQL — usually via dbt.
  • ETL costs an extra piece of infrastructure to operate; ELT simply borrows the target store's compute.
  • A lake is by nature "store raw, structure at read time", so ELT fitting lakes is inevitable.
05

Safe reruns

Every pipeline gets rerun eventually — so the real question is whether running it twice gives the same result.

  • A plain INSERT step is not idempotent: one retry and revenue doubles.
  • Delete the exact partition and rewrite, overwrite by key, or write a new table and rename.
  • Log every run: how many rows came in, how many were rejected, how long it took.
  • Idempotency only ensures a rerun makes nothing worse — whether the numbers are right is another matter.
06

Batch and stream

The same pipeline, only a different cadence — but going from hours to seconds drags in three things batch never has to think about.

  • Batch: gather and run on a schedule; if wrong, rerun the whole batch; latency in hours.
  • Stream: process each event as it arrives; latency in seconds; infrastructure runs 24/7.
  • Between the extremes sits micro-batch: still batch, but small batches run every few minutes.
  • Choose by the latency the business can accept, not by which technology is newer.
07

Windowing and late events

A data stream has no end point — so an "hourly total" means cutting your own windows, and windows sometimes close at the wrong moment.

  • Tumbling windows sit back to back; sliding windows overlap, so they update more often.
  • Out-of-order events make results wrong without raising any error — which makes them the hardest to detect.
  • You must distinguish event time (when it happened) from processing time (when it was received).
  • The watermark decides how long to wait: wait long and you are late, wait short and you lose data.
08

Quality dimensions

"Good data" is too vague to check — six dimensions break it into true/false questions, one query each.

  • The first five dimensions can be checked with COUNT, DISTINCT, IS NULL — no new tools needed.
  • But passing all five does not imply the data is right: they only measure form.
  • Only the sixth, accuracy, measures content — and it is the only one that cannot be automated.
  • So accuracy is checked with business rules, not technical rules.
09

Where to check

The closer to the source, the cheaper the check — three checkpoints, each catching a kind of error the next one can no longer catch.

  • At the source: database constraints block bad data at write time, but only for data you own.
  • In the pipeline: run the six-dimension checks on the staging table before pushing to the main table.
  • At the point of use: catch wrong transform logic — every source table is valid yet the final number is still absurd.
  • The three checkpoints catch three different kinds of error — none can replace another.
