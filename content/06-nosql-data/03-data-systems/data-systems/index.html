Data systems

Data travels from where the application writes it to where analysts read it. Four things to remember:

  • where to store it — a warehouse enforces schema up front, a lake at read time
  • how to move it — ETL or ELT; a rerun must give the same result
  • what cadence — batch or stream, chosen by the business's latency needs
  • are the numbers right — a green pipeline does not mean correct data
01

Mental model

The app writes rows one at a time; a pipeline copies them to a separate store built for reading many rows at once.

  • The write side is the OLTP database; the read side is a warehouse or lake.
  • Analysts never query the app database — a big scan would slow every user down.
02

Storage

Both clean data and enforce a schema — they differ in when that cost is paid.

  • Most companies run both: raw data lands in the lake, settled questions move to the warehouse.

2.1Warehouse

Schema on write: bad rows are rejected before storage, reading is plain SQL.

  • You must know the questions up front.

2.2Lake

Schema on read: files are stored as-is in cheap storage, structure is worked out per query.

  • Cheap and flexible, but every reader must know what each file means.
03

Star schema

One fact table of keys and numbers in the middle, dimension tables around it to slice by.

  • One level of JOIN, so aggregates are fast — a deliberate denormalization.
  • A snowflake schema splits dimensions further: less duplication, more JOINs.
04

Pipeline

A pipeline moves data through layers of cleanliness — and must survive being rerun.

4.1Raw, cleaned and mart

Each layer is a level of cleanliness, not a redundant copy.

  • raw stays as-is so a wrong pipeline can be rebuilt.
  • cleaned is the one shared truth; mart is pre-aggregated per team.

4.2ETL

Transform in a separate engine, then load only clean rows.

  • Classic for warehouses; costs one more system to run.

4.3ELT

Load raw rows first, then transform inside the store with SQL — usually dbt.

  • Borrows the store's compute; natural for lakes and modern warehouses.

4.4Idempotent reruns

Every job gets retried — running it twice must give the same result.

  • Delete the partition then insert, overwrite by key, or write a new table and swap.
05

Processing

Same pipeline, different cadence — chosen by the latency the business can accept.

5.1Batch

Gather all day, run one job on a schedule.

  • A wrong result means rerunning the batch; latency in hours.
  • Micro-batch runs small batches every few minutes.

5.2Stream

Process each event the moment it arrives.

  • Latency in seconds; the job runs 24/7.

5.3Windows and late events

A stream never ends, so "per 5 minutes" means cutting windows on event time.

  • Tumbling windows sit back to back; sliding windows overlap.
  • The watermark decides how long to wait for late events: too short loses data, too long delays results.
06

Data quality

A green pipeline does not mean correct data — quality is checked explicitly.

6.1Quality dimensions

Six true/false questions: completeness, uniqueness, validity, consistency, timeliness, accuracy.

  • The first five need only COUNT, DISTINCT, IS NULL.
  • Accuracy needs a business rule.

6.2Where to check

The closer to the source, the cheaper the check.

  • At the source: constraints; in the pipeline: tests on staging; at use: sanity checks on the final number.
