Database · data systems

OLTP vs OLAP

One system for transactions, one for analytics. Three things to remember:

  • OLTP touches a few rows in milliseconds; OLAP scans millions of rows and aggregates
  • they differ down at the disk layer: row-oriented vs column-oriented
  • split the systems because the two workloads compete for CPU and snapshots
01

Mental model

OLTP runs many tiny writes; OLAP runs a few huge scans.

  • OLTP (online transaction processing): orders, logins, stock — answer in milliseconds.
  • OLAP (online analytical processing): reports and dashboards — seconds are fine.
02

Storage layout

The same table can sit on disk row by row or column by column.

2.1Row-oriented

One row is one block — great for writing or reading a whole record, wasteful for one column.

  • Used by OLTP databases: PostgreSQL, MySQL.

2.2Column-oriented

One column is one block — a query reads only the columns it names.

  • Used by warehouses: BigQuery, Snowflake, ClickHouse, Parquet files.
  • One column holds one type, often repeated, so it compresses well.
  • Cost: inserting one row touches every column block.
03

Schema shape

OLTP keeps each fact once; OLAP copies it into one wide table.

  • Normalized tables make writes safe: rename a customer in one row.
  • The wide table makes reads fast: no JOIN at query time. The common shape is the star schema.
04

Why split the systems

A big report on the app database slows real users — so copy the data out.

  • ETL (extract, transform, load) copies data into the warehouse on a schedule.
  • Cost: the warehouse is only as fresh as the last load — hours old is normal.
  • For light reports a read replica is often enough.
