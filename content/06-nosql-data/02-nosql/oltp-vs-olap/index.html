Database · data systems

OLTP vs OLAP

One system for transactions, one for analytics. Three things to remember:

  • OLTP touches a few rows in milliseconds; OLAP scans millions of rows and aggregates
  • they differ down at the disk layer: row-oriented vs column-oriented
  • split the systems because the two workloads compete for CPU and snapshots
01

OLTP and OLAP workloads

OLTP optimizes for writes and point lookups, OLAP optimizes for reading large blocks and aggregating — two nearly opposite goals.

  • OLTP: very many statements, each touching a few rows, must finish in milliseconds.
  • OLAP: very few statements, each touching millions of rows; a few seconds of latency is fine.
  • The fix is not clever tuning but splitting into two systems joined by a pipeline.
  • This is where the course leaves the single database and looks at data at company scale.
02

Row-oriented and column-oriented

The deepest difference is how data is laid out on disk — which decides what a single disk access reads.

  • Row-oriented: the whole row sits contiguously, good for writing and reading a full record.
  • Column-oriented: the whole column sits contiguously, so SUM over one column skips the other 39.
  • A column holds values of one type, so it compresses very well — another IO win.
  • Because they differ at the disk layer, no single system does both well.
03

Schema shape

The same data exists in two shapes — because normalization pays off for writes, and OLAP barely writes.

  • OLTP normalizes: each fact in one place, change it once and you are done — fits because it writes constantly.
  • OLAP denormalizes: names are copied into a wide fact table so aggregation needs no JOIN.
  • Duplicate data here is not a bug — its cost (update anomalies) does not arise on the OLAP side.
  • The real cost is that data is only as fresh as the last load; hours stale is normal.
04

Why split the systems

Running reports directly on the production database competes for two things — and the second one is often missed.

  • Resource contention: a query scanning tens of millions of rows hogs CPU and IO, and real transactions queue up.
  • Lock contention: a long read holds its snapshot for long, the database must keep every old version, and tables bloat.
  • Light reports → read from a follower; heavy reports → copy to a separate OLAP system.
  • The line is blurring, but the reason to split is two competing workloads, not two technologies.
