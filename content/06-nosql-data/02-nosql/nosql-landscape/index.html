Database · beyond SQL

NoSQL — four families

When to leave the relational database. Three things to remember:

  • four families: key-value · document · wide-column · graph
  • dropping a fixed schema means moving it into code, not getting rid of it
  • NoSQL is designed around queries, not around data
01

NoSQL families

NoSQL is not one thing — four families solve four different problems, and all four give up some of what SQL provides in exchange for scale.

  • Key-value for caches and sessions; document for records that each have their own shape.
  • Wide-column for heavy writes over time; graph for questions that follow relationships across many hops.
  • What gets dropped is usually JOIN, multi-table transactions and a fixed schema.
  • The default is still relational — most systems never hit its limits.
02

Where the schema goes

Dropping a fixed schema is not dropping the schema — it moves from the database into your code.

  • Schema-on-write: the database blocks on write; changing a column requires a migration.
  • Schema-on-read: anything can be written; three years later five shapes coexist.
  • A good fit when records truly differ in shape; a bad fit when you just dread writing migrations.
  • PostgreSQL has a JSONB type you can query inside — the line between the two keeps blurring.
03

Query-driven design

Relational is designed around data; NoSQL is designed around queries — list the questions first, then build the tables.

  • With no JOIN, data is deliberately duplicated across tables.
  • The cost is that every write must go to several places, and the copies briefly disagree — eventual consistency.
  • A new question with no table serving it means building a table and backfilling the data.
  • How data is split across machines is covered in replication & sharding.
04

Combine, don't replace

In practice you rarely switch to NoSQL — you usually put it next to the relational database, each doing one job.

  • Postgres holds the source of truth; Redis holds cache and sessions; Elasticsearch holds the search index.
  • The one rule that keeps it sane: only one place is written directly, everything else can be rebuilt.
  • Two places written directly is when you stop knowing which number to trust.
  • Every added database is a sync path that can break — add one when you measure a bottleneck, not because it sounds cool.
