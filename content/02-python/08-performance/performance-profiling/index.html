Profiling & performance

Quy tắc duy nhất: đo trước, sửa sau. Chỗ bạn đoán là chậm gần như luôn không phải chỗ chậm thật.

01

Đo trước, đoán sau

Tối ưu mà không đo là sửa mò. Ba công cụ, ba mức chi tiết.

# 1 — nhanh nhất: đo một đoạn
import time; t = time.perf_counter(); ...; print(time.perf_counter() - t)

# 2 — cProfile: hàm nào tốn bao nhiêu
python -m cProfile -s cumtime script.py | head -20

# 3 — line_profiler: từng DÒNG trong một hàm
@profile
def hàm_chậm(): ...     # rồi chạy: kernprof -l -v script.py
  • Đọc cột cumtime trước — tổng thời gian gồm cả hàm con. Nó chỉ thẳng ra nhánh đắt.
  • tottime là thời gian trong thân hàm, không tính hàm con — dùng để tìm hàm tự nó chậm.
  • Đo trên dữ liệu thật. Dữ liệu nhỏ thường cho kết luận ngược.
02

Bộ nhớ

Mỗi object Python có phần thừa cố định. Nhiều object nhỏ tốn hơn bạn tưởng rất nhiều.

một số nguyên~28 byte
list rỗng~56 byte
object thường~152 byte (có __dict__)
object có __slots__~56 byte

số ước lượng trên CPython 64-bittriệu object nhỏ → chênh nhau cả trăm MB

  • __slots__ bỏ __dict__ của instance → gọn hơn và truy cập nhanh hơn, đổi lại không thêm thuộc tính mới lúc chạy được.
  • Đo bằng tracemalloc (thư viện chuẩn) hoặc memory_profiler.
  • Đọc file lớn thì duyệt theo dòng hoặc dùng generator — đừng read().split() cả file.
03

NumPy vectorization

Vòng lặp Python chậm vì mỗi phép tính đi qua tầng thông dịch. NumPy đẩy cả vòng lặp xuống C.

Vòng lặp Python

Mỗi bước: kiểm kiểu, cấp phát object, tăng bộ đếm tham chiếu.

Dữ liệu rải rác trong bộ nhớ.

NumPy

Một lệnh gọi xuống C, lặp bên trong không qua thông dịch.

Dữ liệu liền khối → tận dụng cache và lệnh SIMD.

# chậm
out = [x * 2 + 1 for x in data]

# nhanh hơn hàng chục lần trên mảng lớn
out = data * 2 + 1          # data là np.ndarray
  • Chỉ đáng khi mảng đủ lớn: mảng vài chục phần tử thì chi phí gọi NumPy còn lớn hơn phần tiết kiệm.
  • Đừng lặp Python trên ndarray — vừa mất lợi thế vừa chậm hơn cả list thường.
04

Tổng kết một hình

Ba mức đo trước, rồi mới tới ba chỗ sửa — và chỗ sửa đắt giá nhất thường là một thao tác O(n) bị giấu, không phải tối ưu vi mô.

  • cumtime vs tottime — ở ①: một cái chỉ ra nhánh đắt, một cái chỉ ra hàm tự nó chậm.
  • O(n) bị giấu — ở ②: chỗ sửa đáng giá nhất, vì hàm chiếm 2% thời gian có nhanh gấp đôi cũng chỉ được 1%.
  • __slots__ — ở ②: bỏ __dict__ của instance, đổi lại không thêm được thuộc tính lúc chạy.
  • Vectorization — ở ③: đẩy cả vòng lặp xuống C, nên chỉ có lãi khi mảng đủ lớn để bù chi phí gọi.
05

Lỗi hay gặp

Lỗi đầu tiên tốn nhiều thời gian nhất mà không đổi được gì.

Tối ưu chỗ không phải bottleneck

Hàm chiếm 2% tổng thời gian, tối ưu nhanh gấp đôi cũng chỉ tiết kiệm 1%. Đo trước.

Bỏ qua thao tác O(n) bị giấu

x in list, list.pop(0), s += "a" trong vòng lặp. Sửa mấy dòng này thường ăn đứt mọi tối ưu vi mô.

Đo trên dữ liệu đồ chơi

Với n nhỏ thì cache và hằng số quyết định, kết luận có thể ngược hẳn khi n lớn.

06

Hỏi đáp

Tự nghĩ ra ý trả lời trước rồi mới mở — cốt là hiểu ý, không phải thuộc chữ.

Code Python chậm, bạn làm gì đầu tiên?

Đo bằng cProfile trên dữ liệu thật, đọc cumtime để tìm nhánh đắt nhất. Chưa đo thì chưa sửa.

Vì sao vòng lặp Python chậm hơn NumPy?

Mỗi phép tính phải qua tầng thông dịch và tạo object mới. NumPy chạy vòng lặp trong C trên vùng nhớ liền khối.

__slots__ để làm gì?

Bỏ __dict__ của instance → tốn ít bộ nhớ hơn và truy cập nhanh hơn, đổi lại không thêm thuộc tính mới lúc chạy được.
