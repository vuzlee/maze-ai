Python · performance

Profiling & performance

Optimising without measuring is guessing.

  • measure first — the slow part is rarely where you think
  • speeding up 1% of the runtime is wasted work
  • big, uniform numeric data → vectorize
01

Measure first

A function called more often is not always the slow one. Only a measurement tells.

python -m cProfile -s cumtime app.py

  • cProfile: time per function · line_profiler: time per line.
  • Profilers slow the program down — compare shares; time small snippets with timeit.
  • Memory: tracemalloc. Production: a sampling profiler such as py-spy.
02

Reading cProfile output

Sort by cumtime, then compare it with tottime to find the function that is slow by itself.

  • tottime: time in the function's own body · cumtime: including everything it calls.
  • percall = time ÷ ncalls.
03

Vectorize

A Python loop sends every element through the interpreter. NumPy runs the whole loop in C.

3.1One step per item vs one call

The loop doubles each item through the interpreter; b * 2 hands the whole array to C in one call.

3.2Measured cost

On 1 million numbers the single C call is 46× faster and uses a quarter of the memory.

  • A list holds separate objects; an ndarray is one block of raw numbers.
  • Pays off only for large, uniform data — small arrays lose to the setup cost.
  • Background: Memory model & mutability.
04

Optimisation order

Go from cheap to costly and stop when it is fast enough.

  • Step 2 usually wins: in list → in set was about 16 000× faster here.
  • Measure again after every change, and keep the tests passing.
