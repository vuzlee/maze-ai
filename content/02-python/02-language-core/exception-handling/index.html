Exception handling

Python raises errors instead of returning error codes.

  • an error travels up to the first matching except
  • nobody catches it → the program stops with a traceback
  • catch specific types, subclasses first
01

Mental model

An exception is an object that travels up the call chain and stops at the first matching except.

  • The handler does not have to sit next to the code that fails.
  • Python also uses exceptions for normal flow: StopIteration ends a for loop, KeyError reports a missing dict key.
02

The try statement

try guards code; the other blocks say what runs next.

2.1except

Runs when the guarded code raises a matching error; the rest of try is skipped.

except ValueError as e: — e is the error object.

  • Keep try short — wrapping a whole function catches errors from the wrong line.

2.2else

Runs only when try raised nothing.

  • Keeps the follow-up code out of the guarded part.

2.3finally

Runs always — even after return, even while an error is still rising.

  • For files and locks, with is shorter — see Decorator & context manager.

2.4Both paths

No error: try → else → finally. Error: try → except → finally.

03

Exception hierarchy

except also catches subclasses, so the first matching block wins — put subclasses first.

  • A parent listed first turns the lower block into dead code, with no warning.
  • Bare except: also catches KeyboardInterrupt and SystemExit — use except Exception.
  • Catching broadly without re-raising swallows the error: the program goes on in a bad state.
04

raise from

Wrapping an error in your own type? Write raise … from e to mark the cause.

  • __cause__ holds the original error; the traceback prints both, linked as the direct cause.
  • A bare raise inside except re-raises the same error with its traceback.
05

Custom exceptions

One base class for your app; callers choose to catch one type or the whole family.

class AppError(Exception): pass · class NotFound(AppError): pass
