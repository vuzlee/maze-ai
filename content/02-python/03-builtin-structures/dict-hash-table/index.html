Python dict & hash table

A lookup is not a search.

  • the hash gives the slot; no other key is compared
  • a collision probes on; a delete leaves a tombstone
  • past 2/3 full the table doubles and every key is rehashed
01

Mental model

Each key knows its own slot: hash(k) % size gives the slot with no comparisons.

  • The time stays flat as the table grows — that is what O(1) means.
  • Keys must be hashable: {[1]: 0} raises TypeError.
  • Equal keys merge: {1: 'a', True: 'b'} is {1: 'b'}, because 1 == True.
02

Collision

Two keys in the same slot is a collision; the later key probes on to a free slot.

  • CPython uses open addressing, not the chaining (linked lists) of textbooks.
  • Its real probe jumps by a pseudo-random step, not always to the next slot — same idea.
03

Tombstone

Emptying a slot on delete cuts the probe sequence, so a delete leaves a tombstone.

  • Lookups walk past a tombstone; inserts may reuse its slot.
  • Many deletes slow lookups down — rebuild with d = dict(d).
04

Resize

Past a load factor of 2/3, CPython doubles the table and rehashes every key.

  • A resize is O(n) but rare, so an insert stays O(1) amortized.
05

Insertion order

The hash scrambles slots; an entries array keeps insertion order.

  • Guaranteed since Python 3.7. Delete and re-add moves a key to the end.
  • Adding keys while iterating raises RuntimeError — iterate over list(d).
  • A set has no entries array, so it keeps no order.
