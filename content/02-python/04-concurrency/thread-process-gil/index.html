Process, thread & GIL

Gộp phần hệ điều hành và phần Python. Bốn thứ cần nhớ:

  • core → scheduler → process → thread: bốn tầng lồng nhau
  • process có bộ nhớ riêng, thread dùng chung
  • GIL: mỗi lúc chỉ một thread chạy bytecode Python
  • CPU-bound thì dùng process, IO-bound thì thread vẫn ăn tiền
01

Ai chứa ai

Bốn tầng lồng nhau: core chạy một luồng lệnh, OS scheduler chia lát thời gian, process là ranh giới bộ nhớ, thread là đơn vị được lên lịch.

  • Một core mỗi lúc chạy đúng một luồng lệnh. Nhiều thread hơn core thì phải thay phiên nhau.
  • Process chứa 1 hay nhiều thread. Thread không tồn tại ngoài process nào.
  • Thread cùng process dùng chung heap, biến global và file descriptor.
  • Riêng stack, register và program counter — để mỗi thread biết đang chạy dòng nào.
  • Máy đo bài này chỉ có 1 core, nên mọi số liệu dưới đây là trên một core.
02

Bộ nhớ

Ranh giới cô lập quyết định tất cả: thread dùng chung một vùng nhớ, process mỗi cái một bản riêng.

  • Đo thật: thread sửa dict thì luồng cha thấy ngay (42); process sửa bản sao thì cha vẫn thấy 0.
  • Chung bộ nhớ là ưu điểm, cũng là nguồn race condition — nên thread cần lock còn process thì không.
  • Một process crash không kéo process khác chết theo; một thread crash thì có thể kéo cả process.
  • Truyền dữ liệu giữa process phải pickle và đi qua IPC.
  • 200.000 số mất 3.2 ms đóng gói + 9.5 ms mở, 0.9 MB qua ống.
03

Context switch

Đổi giữa hai thread cùng process chỉ cần đổi register và stack. Đổi sang process khác phải đổi cả bảng trang.

  • Đo ping-pong: 2 thread 10.1 µs mỗi lượt, 2 process qua Pipe 16.3 µs.
  • Chi phí tạo chênh nhiều hơn: 1 thread 39 µs, 1 process 1.31 ms — đắt hơn 34 lần.
  • Vì tạo process phải nhân bản bảng trang và cấu trúc của nhân.
  • Đổi bảng trang còn làm TLB và cache mất hiệu lực, nên chi phí thật cao hơn con số đo được.
04

Scheduling

Thread ở một trong ba trạng thái, và chỉ running mới thật sự ở trên core.

  • Ready xếp hàng chờ, running đang chạy, blocked đợi IO và không tốn CPU.
  • Linux dùng lập lịch preemptive: scheduler cắt được bất cứ lúc nào, không đợi thread nhường.
  • Nên đừng giả định một đoạn code chạy liền mạch — nó bị cắt giữa chừng khi hết time slice.
  • Đây chính là gốc của race condition: đúng lúc bị cắt thì giá trị đang sửa dở.
05

GIL

GIL (Global Interpreter Lock) là một khoá toàn cục: mỗi lúc chỉ một thread chạy bytecode Python.

  • Đo thật: 1 việc mất 294 ms, 4 việc trên 4 thread mất 1190 ms — đúng 4.1 lần.
  • Nghĩa là thêm thread không làm CPU-bound nhanh lên, chỉ chia nhỏ cùng một lượng thời gian.
  • GIL tồn tại vì ob_refcnt của mọi object phải sửa an toàn — xem Memory management & GC.
  • GIL được nhả mỗi 5 ms, hoặc ngay khi thread vào IO.
  • Thư viện C như NumPy cũng nhả GIL khi tính toán, nên phần đó song song thật.
06

IO-bound

Thread đợi IO thì nhả GIL — nên nhiều thread cùng đợi được, và đây là chỗ thread thắng rõ.

  • Đo thật: 8 việc IO tuần tự mất 1601 ms, 8 thread chỉ mất 201 ms — nhanh hơn 8.0 lần.
  • Vì phần lớn thời gian là ngồi đợi mạng hay đĩa, không giữ GIL.
  • Nhưng mỗi thread tốn vài trăm KB stack, nên vài nghìn kết nối thì nên dùng async — xem Async / asyncio.
