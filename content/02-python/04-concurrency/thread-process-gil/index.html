Python · concurrency

Process, thread & GIL

The OS side and the Python side in one place.

  • core → scheduler → process → thread, nested
  • a process has its own memory; threads share it
  • the GIL lets one thread run Python bytecode at a time
  • CPU-bound: processes; IO-bound: threads still help
01

Mental model

Four nested layers: a core runs, the OS scheduler slices time, a process walls off memory, a thread gets scheduled.

  • A process holds one or more threads; a thread never lives outside a process.
  • Threads share the heap and globals; each has its own stack and registers.
02

Memory

Threads share one memory; each process has its own copy.

  • Sharing causes race conditions, so threads need a lock; processes do not.
  • A crashing process does not take others down; a crashing thread can.
03

Context switch

Switching threads swaps registers and stack; switching processes also swaps page tables.

  • Creating one differs more: thread 39 µs, process 1.31 ms.
04

Scheduling

A thread is ready, running or blocked — only running is on the core.

  • Linux is preemptive: a thread is cut off mid-code when its time slice ends.
  • Blocked threads cost no CPU — why IO-bound work suits threads.
05

GIL

The GIL (Global Interpreter Lock): one thread runs Python bytecode at a time.

  • More threads do not speed up CPU-bound Python; they split the same time.
  • It protects every object's reference count — see Memory management & GC.
  • C libraries such as NumPy release it while computing.
06

IO-bound work

A thread waiting on IO releases the GIL, so many threads can wait at once.

  • Thousands of connections? Use asyncio instead of thousands of stacks.
07

Choosing a model

One question: does the job compute or wait?

with ProcessPoolExecutor() as ex: results = list(ex.map(work, items))

  • Measure first — guessing the job type optimises the wrong thing.
  • Python 3.13 has an experimental free-threaded build without the GIL.
