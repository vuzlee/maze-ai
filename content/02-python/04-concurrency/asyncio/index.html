Python · concurrency

Async / asyncio

One thread, many tasks, switching at each await.

  • await hands control back to the event loop
  • one blocking call freezes the whole loop
  • async does not make code faster; it lets you wait on many things at once
01

Mental model

All tasks share one thread; await says "I am waiting — run someone else".

await asyncio.gather(fetch(a), fetch(b))

  • Awaiting one by one still queues; gather or create_task overlaps.
  • Calling work() without await only creates a coroutine — its body never runs.
  • Keep a reference to every create_task(...), or the task may be garbage-collected.
02

Event loop

asyncio.run() creates one loop, runs it pass after pass, then closes it.

2.1Lifecycle

Create → run → clean up → close, exactly once.

  • One loop per process — each asyncio.run call builds a new one.

2.2One loop pass

Each pass waits in select first, then runs ready callbacks.

  • An idle loop sleeps in select (epoll) — it does not poll.
  • A callback added during a pass runs on the next pass.

2.3Shutdown

Closing cancels pending tasks, and a closed loop never reopens.

  • gather your tasks before main() returns.
  • asyncio.run inside a running loop raises RuntimeError.
03

Blocking calls

A sync call holds the only thread, so the whole loop stops.

await asyncio.to_thread(requests.get, url)

  • Sync libraries (requests, many DB drivers) block — use async ones or to_thread.
  • CPU-bound work blocks the same way; move it to a process.
04

Cost per task

A task is a small object; a thread reserves a whole stack.

  • So thousands of open connections suit asyncio, not threads.
  • The catch: every library in the chain must be async.
  • Choosing between process, thread and asyncio: Process, thread & GIL.
