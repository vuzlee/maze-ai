Async / asyncio

Async đổi đơn vị chờ từ một luồng 8 MB sang một object vài trăm byte — đó là toàn bộ lý do nó tồn tại. Đổi lại, một lệnh chặn duy nhất treo cả event loop. Bài này đi qua ba lỗi async kinh điển, chi phí thật của từng mô hình, và bảng chọn cuối cùng.

01

Async giải quyết chuyện gì mà thread không

Cùng là để chờ I/O, nhưng async đổi đơn vị chờ từ luồng hệ điều hành sang một object vài trăm byte.

  • Một luồng tốn khoảng 8 MB stack và mỗi lần chuyển luồng phải đi qua nhân. 1000 kết nối đồng thời là 1000 luồng — không kham nổi.
  • Một coroutine đang chờ chỉ là một object trong event loop. Đổi lại: chỉ cần một lệnh chặn là treo cả vòng lặp, ảnh hưởng mọi request khác.

02

async/await

Đồng thời hợp tác trên một luồng duy nhất: mỗi tác vụ tự nguyện nhường quyền tại điểm await.

import asyncio

async def fetch(session, url):
    async with session.get(url) as r:
        return await r.text()          ← nhường quyền tại đây

async def main(urls):
    async with aiohttp.ClientSession() as s:
        return await asyncio.gather(*[fetch(s, u) for u in urls])

asyncio.run(main(urls))                # 1000 request đồng thời trên MỘT luồng

gatherChạy nhiều thứ đồng thời và chờ tất cả xong

Vì sao async nhẹ hơn thread nhiều lần

Một luồng hệ điều hành tốn khoảng vài MB ngăn xếp và mỗi lần chuyển luồng phải đi qua kernel. Một task async chỉ là một object Python vài KB, và chuyển đổi chỉ là một lần gọi hàm trong không gian người dùng. Đó là lý do 10.000 kết nối đồng thời khả thi với async nhưng vô vọng với thread.
03

Ba lỗi async kinh điển

1. Gọi hàm chặn trong event loop

async def handler():
    time.sleep(2)              ← ĐÓNG BĂNG TOÀN BỘ event loop 2 giây
    data = requests.get(url)   ← cũng vậy: thư viện đồng bộ
    row = cursor.execute(sql)  ← driver DB đồng bộ cũng vậy

# đúng:
async def handler():
    await asyncio.sleep(2)
    data = await client.get(url)                     # thư viện async
    row = await asyncio.to_thread(cursor.execute, sql) # đẩy hàm chặn sang thread

Đây là lỗi nghiêm trọng nhất vì hậu quả không nằm ở một request — nó làm mọi request đang chờ bị treo theo. Triệu chứng: server chậm bất thường dưới tải mà CPU vẫn thấp.

2. Quên await

result = fetch(url)          ← không chạy gì, result là một coroutine object
result = await fetch(url)    # đúng

Python cảnh báo coroutine was never awaited — nhưng chỉ khi bộ thu gom rác dọn tới nó, nên cảnh báo hiện muộn và ở chỗ khác hẳn nơi gây lỗi.

3. Tuần tự hoá vô tình

# SAI: chờ xong từng cái → không nhanh hơn tuần tự
for url in urls:
    results.append(await fetch(url))

# ĐÚNG: phát hết ra rồi chờ chung
results = await asyncio.gather(*[fetch(u) for u in urls])

Chi tiết ít người biết

Nếu một tác vụ trong gather ném lỗi, các tác vụ khác vẫn tiếp tục chạy và lỗi được ném lên ngay. Dùng return_exceptions=True để nhận lỗi như một giá trị kết quả thay vì làm sập cả nhóm. Đây là điều bắt buộc phải xử lý trong code thật.

06

Trong hệ thống thật

Một API phục vụ model LLM:

  uvicorn --workers 4          ← 4 TIẾN TRÌNH, thoát GIL, dùng 4 lõi
    └── mỗi tiến trình: 1 event loop
          ├── async: nhận request, gọi vector DB, gọi LLM API, stream về client
          └── to_thread: gọi driver DB đồng bộ, đọc file, xử lý ảnh

Đây là kiến trúc gặp ở gần như mọi service Python hiện đại, và nó dùng cả ba mô hình đúng chỗ: process để dùng nhiều lõi, async để chồng lấn hàng nghìn lần chờ, thread để chứa những thư viện chưa có bản async.

Câu hỏi hay gặp ở vòng system design

Service của em xử lý được bao nhiêu request đồng thời? Câu trả lời tốt bắt đầu bằng việc phân loại: nếu chủ yếu là chờ, giới hạn nằm ở kết nối và bộ nhớ nên async cho phép hàng nghìn; nếu chủ yếu là tính, giới hạn nằm ở số lõi và không mô hình nào vượt qua được — phải scale ngang.
07

Lỗi hay gặp

Ba lỗi này làm code async chạy đúng nhưng chậm như tuần tự, hoặc mất task im lặng.

Gọi hàm chặn trong coroutine

Treo cả event loop, ảnh hưởng mọi request khác. Bọc bằng asyncio.to_thread.

await trong vòng lặp

Thành tuần tự. Dùng gather để phát hết rồi chờ chung.

Tạo task rồi không giữ tham chiếu

asyncio.create_task mà không lưu lại thì task có thể bị thu gom giữa đường. Giữ trong một set, hoặc dùng TaskGroup.

08

Hỏi đáp phỏng vấn

Tự trả lời thành tiếng trước, rồi mới mở ra.

Thread, process, async — bạn chọn thế nào?

Tôi phân loại tác vụ trước bằng cách so thời gian CPU với thời gian thực tế. Nếu chờ nhiều thì async, vì mỗi task chỉ vài KB nên chồng lấn được hàng nghìn kết nối; nếu thư viện chỉ có bản đồng bộ thì thread, vì không phải viết lại code. Nếu tính nhiều thì process, đó là cách duy nhất dùng nhiều lõi — nhưng phải chia thành khối lớn để bù chi phí pickle. Trong service thật thì thường dùng cả ba: nhiều tiến trình, mỗi tiến trình một event loop, và thread pool cho các thư viện chặn.

Vì sao 1000 kết nối đồng thời thì async chứ không thread?

Vì chi phí mỗi đơn vị. Một luồng hệ điều hành tốn khoảng 8MB ngăn xếp và mỗi lần chuyển luồng phải đi qua kernel; 1000 luồng là gần 8GB RAM và rất nhiều context switch. Một task async chỉ là object Python vài KB, chuyển đổi là một lần gọi hàm trong không gian người dùng. Cùng mức đồng thời, async tốn ít hơn hai bậc độ lớn. Đánh đổi là toàn bộ chuỗi hàm phải viết theo kiểu async và không được có lệnh chặn nào.

Trong FastAPI, khi nào bạn dùng def và khi nào async def?

Dùng async def khi mọi lệnh I/O bên trong đều có bản async — client HTTP async, driver DB async. Dùng def thường khi hàm có lệnh chặn: framework sẽ tự chạy nó trong một thread pool nên không treo event loop. Lỗi tệ nhất là khai báo async def rồi gọi thư viện đồng bộ bên trong — lúc đó event loop bị đóng băng và mọi request khác chờ theo. Nếu buộc phải gọi lệnh chặn trong coroutine thì bọc bằng asyncio.to_thread.
