TCP & HTTP

Reliable bytes, and what to do when a call fails.

  • TCP opens a connection and resends lost data
  • HTTP is a request and a response sent over it
  • retry with backoff and jitter, only when the call is idempotent
01

Mental model

TCP is a reliable pipe; HTTP is the request and response sent through it.

  • Request = method, path, headers, optional body. Response = status, headers, body.
02

TCP

Bytes arrive complete and in order — or the connection reports an error.

2.1Three-way handshake

Agree to talk before sending data.

  • That round trip is why reusing a connection (keep-alive) is faster.

2.2Retransmission

Every segment is numbered; a missing one is sent again.

2.3UDP

The alternative: just send, no guarantees.

03

HTTP versions

Each version gets more done per connection.

3.1HTTP/1.1

One request at a time on a connection.

  • Browsers open about 6 connections per site to work around it.

3.2HTTP/2

Many requests at once on one TCP connection.

  • The catch: TCP delivers in order, so one lost packet blocks all streams (head-of-line blocking).

3.3HTTP/3

Runs on QUIC over UDP — streams don't block each other.

  • QUIC also merges the TCP and TLS handshakes: one round trip fewer.
04

Retries

Networks fail — retry, but without making things worse.

4.1Exponential backoff

Wait twice as long after each failure.

  • Retry only temporary errors: timeout, 429, 503 — never 400 or 404.

4.2Jitter

Add randomness so clients don't retry together.

4.3Idempotency

Doing it twice must have the same effect as once.

  • GET, PUT, DELETE are idempotent; POST is not — give it an Idempotency-Key header.

4.4Circuit breaker

After repeated failures, fail fast instead of waiting.

  • Without it, every caller waits for timeouts and the failure spreads (cascading failure).
  • Pair it with a fallback: cached data or a reduced answer.
