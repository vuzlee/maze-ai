Hash map & set

The most-used tool in real problems: trade memory for time, turning O(n²) into O(n).

01

Mental model

No searching — compute the position directly: slot = hash(key) % n_slots. So looking up a key among 10 keys or 10 million keys takes the same 0.024 µs.

  • O(1) does not mean “fast”; it means n does not appear in the formula. At small n, scanning a list straight through is even faster because there is no hashing.
  • You pay with memory (the table always keeps ~1/3 empty) and with order: every question like “smallest”, “next”, “in range” has to move to a tree or a sorted array.
  • set is a dict without the values — same mechanism, same cost. The internals (probing, tombstones, resizing) are in Python dict & hash table.
02

When O(1) stops being O(1)

Two keys landing in the same slot is a collision — normal, and in a roomy table one or two probes settle it. The danger lies in three other places, and none of them raise an error; things just get slower.

  • Same slot is not same hash. With the same slot, one probe separates them; with the same hash, two keys walk exactly the same path — that is the real root of O(n).
  • In interview problems keys are plain int, str, tuple, so the “evil key” column almost never happens. It happens when you write your own __hash__, or when someone else picks the input.
  • Python uses open addressing (probe other slots in the same array), Java uses chaining (each slot holds a list). Python's way is faster because the slots are contiguous, but it must keep the table roomy — hence the 2/3 cap.
03

Trading memory for time

This is the move that makes hash maps worth learning: remember what you've already passed so you never go back to look — O(n²) drops to O(n). But it only pays off when the data has no existing structure to exploit.

def two_sum(a, target):
    seen = {}                        # value already seen -> index
    for i, x in enumerate(a):
        if target - x in seen:       # seen the complement yet?
            return seen[target - x], i
        seen[x] = i                  # record, then move on
  • One pass, not two. Record seen[x] = i after asking, so an element is never paired with itself — no second loop needed.
  • The price is O(n) memory: 100,000 keys cost 5 MB. A memory constraint in the problem, or a sorted array, is a hint to switch to two pointers.
  • The same move comes back in prefix sum (remember sums already seen) and sliding window (remember characters currently in the window).
04

Common mistakes

None of the four mistakes below throws an exception. They return results that still look plausible — so you have to spot them by eye, not by traceback.

1, 1.0 and True are one key

{1:'a', 1.0:'b', True:'c'} gives {1: 'c'}, len is 1. Because hash(1) == hash(1.0) == hash(True) and the three values are equal.

Counting frequencies over data mixing int and bool silently merges them.

Reading a defaultdict creates the key

d = defaultdict(int); just reading d['x'] makes len(d) jump from 0 to 1.

Check with if k in d, not if d[k]. Counter does not have this problem.

Mutating a key after inserting it

If its hash changes it still sits in the old slot — lookups never find it again, while len is still right and printing still shows the element.

Details in List, tuple & set.

Relying on set order

dict keeps insertion order since 3.7; set does not. Worse: set([1,2,3,4,5]) happens to iterate in order, so small tests pass and the bug only shows up on real data.
