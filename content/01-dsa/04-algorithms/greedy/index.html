Greedy

The shortest code of any technique, and also the technique easiest to get wrong without knowing it.

01

Mental model

Pick the locally best option, never go back, never consider alternatives. When it is right it is extremely cheap; when it is wrong it fails silently.

02

When greedy is right

It needs two properties. Missing one means switching to dynamic programming.

1 · Greedy choice is safeThere exists an optimal solution that contains the first greedy choice. In other words: choosing it does not lose every best solution.
2 · Optimal substructureAfter choosing, what remains is a smaller problem of the same form, and solving that part optimally is enough.
  • Example where it's right: scheduling, choose the meeting that ends earliest — it leaves the most room for the rest.
  • Making change for 6 with denominations [1, 3, 4]: greedy gives 4 + 1 + 1, the optimum is 3 + 3.
03

How to prove it

No rigorous proof needed. You need two sentences in the right shape — that is what the interviewer is waiting to hear.

Exchange argument

"Suppose an optimal solution does not pick the earliest-ending meeting."

"Swapping its first meeting for the earliest-ending one adds no conflict and the number of meetings does not drop — so the greedy choice is optimal too."

Counterexample

If you can't build the argument above, look for a small counterexample: 3–4 elements is enough.

Found a counterexample → greedy is wrong → switch to DP. That is a good answer too.

being able to say one of the two is enoughsilently writing greedy and saying "I think it's right" loses points

04

Common mistakes

The first trap is the most dangerous: the code runs, passes every sample test, and fails on hidden tests.

Greedy that looks right but is wrong

Passing a few small examples is no proof. Always try unusual data: odd denominations, nested intervals, negative numbers.

Sorting by the wrong key

Meetings are sorted by end time, not start time. Changing the key turns right into wrong.

Ignoring a secondary constraint

Choosing greedily by one criterion while forgetting another constraint (capacity, deadline) — usually you need to add a heap.
