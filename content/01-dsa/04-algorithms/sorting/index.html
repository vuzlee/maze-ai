Sorting

You rarely have to implement one yourself. But knowing which sort key to choose solves half of all greedy and interval problems.

01

Mental model

Sorting is not the goal. It is the preparation step that turns a hard problem into an easy one — and what it buys is not a few percent: at n = 30,000 it is 20.4 seconds down to 5.37 milliseconds.

  • The same trick comes back in many problems: the two closest numbers (once sorted, only adjacent pairs need comparing), merging overlapping intervals (sorted by start, an interval can only overlap the one just before it). Both go from O(n²) to O(n) after sorting.
  • What makes the trick work is transitivity: in a sorted array, knowing b[i]+b[j] is too small is enough to rule out every j'<j without trying them. Sorting is paying up front for the right to reason that way.
  • But it is not free and not always worth it: for the k largest elements a heap is O(n log k), measured 11× cheaper. Ask "do I need the whole order or just a few elements" before typing sort.

03

Bubble, Selection, Insertion

The three everyone learns first. Slow, but one of the three is running inside Python right now.

The three you just watched in the section above, now written as code. Read it alongside the lab and each loop below corresponds to exactly one step you pressed.

# Bubble — swap adjacent pairs until nothing is out of order
for i in range(n):
    for j in range(n - i - 1):
        if a[j] > a[j + 1]:
            a[j], a[j + 1] = a[j + 1], a[j]

# Selection — each round find the smallest, move it to the front
for i in range(n):
    m = min(range(i, n), key=lambda k: a[k])
    a[i], a[m] = a[m], a[i]

# Insertion — take each one, step back and slot it into place
for i in range(1, n):
    x, j = a[i], i - 1
    while j >= 0 and a[j] > x:
        a[j + 1] = a[j]
        j -= 1
    a[j + 1] = x

  • Selection sort loses to Insertion on every count: always O(n²), not stable. It wins in only one place — the fewest swaps, exactly n.
04

Merge, Quick, Heap

No need to memorize the code. You need to know what each one trades for what.

The three fast ones. In the lab they finish in far fewer steps than the three above — the table at the end of this section says why, and what price they pay.

# Merge — split in half, sort both halves, merge back
def merge_sort(a):
    if len(a) <= 1: return a
    m = len(a) // 2
    L, R = merge_sort(a[:m]), merge_sort(a[m:])
    out, i, j = [], 0, 0
    while i < len(L) and j < len(R):
        # <= keeps the old order on ties → stable
        if L[i] <= R[j]: out.append(L[i]); i += 1
        else:           out.append(R[j]); j += 1
    return out + L[i:] + R[j:]

# Quick — pick a pivot, split into three parts around it
def quick_sort(a):
    if len(a) <= 1: return a
    p = a[len(a) // 2]
    lo = [x for x in a if x < p]
    eq = [x for x in a if x == p]
    hi = [x for x in a if x > p]
    return quick_sort(lo) + eq + quick_sort(hi)

# Heap — build a heap, then take the smallest one at a time
import heapq
def heap_sort(a):
    h = a[:]; heapq.heapify(h)          # O(n)
    return [heapq.heappop(h) for _ in h]   # n × O(log n)

05

Why O(n log n) is a lower bound

Each comparison yields only one bit of information. You need enough bits to tell apart the n! possible orderings.

possible orderingsn! ≈ 3.6 million for n = 10
questions neededlog₂(n!) ≈ n log n

each comparison halves the remaining possibilitiesso no comparison-based algorithm can beat n log n

  • This lower bound applies only to comparison-based algorithms.
  • Knowing more about the data breaks it: counting sort, radix sort reach O(n) when the value range is small.
06

Timsort — Python's sort

Textbooks teach Merge and Quick. But the a.sort() you type every day runs Timsort — and it is fast because of a very down-to-earth observation: real data is rarely random.

1 · Find the runsOne pass cuts the array into stretches that are already sorted (runs). A descending stretch gets reversed. Real data — logs, timestamps, data just appended at the end — is full of such stretches.
2 · Short runs get insertion sortA run shorter than 64 elements is extended to length with insertion sort. At that size insertion beats recursion thanks to a small constant and no function-call overhead.
3 · Merge the runsMerge runs pairwise like merge sort, following rules that keep run sizes balanced so it never degrades to O(n²).
ResultRandom data: O(n log n) like merge sort. Already sorted or nearly sorted data: O(n) — a single pass and it's done.

written for Python by Tim Peters in 2002now the default sort in Java, Android, V8, Swift, Rust

  • Timsort is stable — two elements with equal keys keep their original order. That is why sorting by name first and then by score still comes out right.
  • Still, it is safer to sort once with a composite key: a.sort(key=lambda x: (-x.score, x.name)).
  • list.sort() sorts in place, sorted() returns a new list — both are Timsort.
07

Common mistakes

The first trap is the most common mistake when sorting by several keys.

Mixing ascending and descending in a composite key

(-score, name) works because a number can be negated. A string can't be negated — you have to sort twice, relying on stability.

Re-sorting inside a loop

Calling sort() every time you add an element turns an O(n log n) problem into O(n² log n)

And it still gives the right result, just slower as the data grows, so small tests won't catch it. If you need to keep things ordered all the time, use a heap or bisect.insort.

Assuming quicksort is always fast

Already-sorted data + a bad pivot choice → O(n²). The standard library handles it, but if you implement it yourself, pick the pivot at random.
