Replication & sharding

Copy data for safety; split data for size.

  • replication: the same data on several databases
  • sharding: each database holds part of the data
  • choose the shard key carefully — it's hard to change
01

Mental model

Replication copies everything; sharding splits it.

Large systems do both: each shard has its own replicas.

02

Replication

Several copies of one database.

2.1Primary and replicas

Writes go to the primary; replicas copy it and serve reads.

2.2Replication lag

Replicas are a little behind.

Read your own recent changes from the primary.

2.3Failover

If the primary dies, promote a replica.

03

Sharding

Split data across databases by a key.

3.1Range sharding

Split by key range.

Range queries are easy; uneven if some ranges are busier.

3.2Hash sharding

Split by hash of the key.

Even spread; adding a shard with % N moves most keys.

3.3Consistent hashing

Adding a server moves only a few keys.

Used by Cassandra, DynamoDB, Redis Cluster.

3.4Hotspots

A bad shard key sends all traffic to one shard.

  • Good keys spread evenly and appear in most queries — e.g. user_id, not date.
  • Queries without the shard key must ask every shard.
