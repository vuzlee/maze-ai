Inference & cost optimization

Once a model is trained, every remaining problem is systems engineering.

This lesson pins down the difference between prefill and decode — the thing that decides every optimization that follows.

Then how to size the KV cache, why continuous batching multiplies throughput, and a cost-cutting table ranked by payoff.

01

Mental model

Generation is bottlenecked by memory bandwidth, not compute — every technique is a way to fit more tokens into one read of the weights.

A request goes through two phases with opposite characteristics — and every optimization targets only one of them.

Prefill — process the whole prompt in one pass

Many tokens at once → compute-bound. Determines TTFT, the time to first token.

Decode — generate one token at a time

All weights must be read for every token → memory-bound. Determines TPOT, the time per token after that.

prefill lacks compute · decode lacks bandwidthan optimization helps only one phase

Remember one sentence

Prefill lacks compute; decode lacks memory bandwidth. Knowing which phase an optimization acts on tells you whether it helps your problem — and that is what separates a systematic answer from listing tool names.
02

Prefill and decode — why they differ fundamentally

prefill · 2000-token prompt1 read / 2000 tokens — GPU at full capacity
decode · generating token 20011 read / 1 token — GPU waits on memory

compute per byte readdiffers by exactly the number of prompt tokens

15 msone full read of the weights = 14 GB7B model weights in fp16 / 900 GB/smid-range GPU bandwidth

At batch = 1, max generation speed ≈ 65 tokens/second — and this number does not depend on how many FLOPs the GPU has.

The most important consequence of decode being memory-bound

At batch = 1, the GPU reads all the weights just to generate one token. At batch = 32, it reads the same amount of weights but produces 32 tokens. So throughput rises nearly 32× while per-request latency stays almost the same — until you hit the compute limit. This is why batching is the most profitable optimization, and the foundation of every LLM serving system.
03

KV cache

Without a cache

Generating token n recomputes K and V for all n−1 previous tokens → O(n²) cost for the whole sequence, redoing finished work.

With a cache

Store K, V for every processed token; a new token computes only its own K, V and attends to the cache → O(n) cost.

the price is memoryand it is the main constraint of LLM serving

bytesKV cache = 2 · L · nkv · dheadfactor 2 for K and V × seq_len · batch · bytes/valuethe part that grows without bound

A Llama-3-style 8B model (L = 32, nkv = 8, dhead = 128, fp16): each token costs 2 × 32 × 8 × 128 × 2 = 128 KB.

context 8,000 · batch 1~1 GB
context 8,000 · batch 32~32 GB — larger than the model weights

The KV cache usually runs out first, not the weights

Weights are a constant — loaded once, shared by every request. The KV cache scales with batch × context length, so it is the part that grows without bound. On an 80GB GPU serving an 8B model, weights take only 16GB and the remaining 64GB is the KV cache budget — and that number decides how many concurrent requests you can serve.

05

GQA and MQA — shrinking the KV cache through architecture

Why GQA is the most balanced choice

It cuts the KV cache fourfold — i.e. four times as many concurrent requests on the same hardware — with a quality loss that is barely measurable. MQA cuts even more but at a real cost. That nearly every new model picks GQA shows it is the best trade-off in the range, and being able to say so shows you understand architectures are chosen for operational reasons, not just for quality.
06

Batching — static and continuous

Why the gap is so large: response lengths in practice are highly skewed —

Some requests generate 10 tokens, some generate 2000. With static batching, the whole batch is held by the longest request, so most slots in the batch run idle.

Continuous batching delivers several times more throughput on the same hardware, and it is the main contribution of serving engines like vLLM and TGI.

The throughput vs latency trade-off

A large batch gives high throughput but raises TPOT — each decode step has to compute for more requests. So choose by product requirements: a chatbot needs tokens out fast, so keep the batch moderate; bulk processing pushes the batch to the max. Stating this trade-off instead of "bigger batch is always better" is a clear differentiator.
07

PagedAttention

You cannot know in advance how many tokens a request will generate, so the naive approach must allocate the cache for the max length — and most of that space sits empty.

actually used200 tokensholds data
allocated4,096 tokenssits empty

contiguous allocation for the max lengthfragmentation; most allocated VRAM is wasted

Logical cache[block 0][block 1][block 2]… — contiguous from the request's view
Physical cacheblocks scattered across VRAM, joined by a mapping table — like OS paging
Resultallocation on real demand, almost no fragmentation · and requests with the same prefix share blocks

The second benefit — prefix sharing — matters more than it looks.

In practice, thousands of requests often share one long system prompt.

With PagedAttention, the KV cache of that prefix is stored once and every request points to the same blocks, instead of each request keeping its own copy.

The short version

"PagedAttention manages the KV cache in fixed-size blocks, like memory paging, so it does not pre-allocate for the max length — this removes fragmentation and lets many requests share the blocks of an identical prefix. The result is significantly more concurrent requests on the same amount of VRAM."
08

Quantization at inference

What to quantizeEffectNotes
Weights — int8, int4Model 2–4× smaller; faster decode from reading fewer bytesHits exactly where decode is bound: fewer bytes to read
KV cache — int8, fp8Cache 2× smaller → twice the concurrent requestsUsually costs very little quality; worth doing almost always
ActivationNeeded for integer-only hardwareHarder, easily loses quality

Why weight quantization helps speed, not just size

Because decode is bound by memory bandwidth. int4 weights need only 1/4 of the bytes read compared with fp16, so each decode step takes nearly proportionally less time — even though the number of operations is unchanged. Here a memory saving turns directly into a speedup, unlike compute-bound problems. Explaining this mechanism is a systems-level answer.

A measurement caveat: weight-only quantization helps most at small batch sizes, where bandwidth is the bottleneck.

But at very large batch sizes the system becomes compute-bound, so the gain shrinks — and the weights must also be dequantized into a computable format.

09

Speculative decoding

Use a small model to propose several tokens ahead, then the large model checks them all in one forward pass.

1 · Draft model proposesa small, fast model generates k = 4 tokens
2 · Main model verifiesa single forward pass over all 4 of those tokens
3 · Accept up to the first mismatchmatching tokens are kept, everything from the mismatch on is dropped
4 · Repeataccept 3 of 4 → 3 tokens for roughly the cost of 1

Why this works and does not change the result

It works because decode is memory-bound: verifying 4 tokens in one forward pass costs about as much as generating 1 token, since the weights are still read only once.

Compute capacity that used to sit idle is now put to use.

The result is unchanged because the acceptance rule is designed so the output distribution is identical to normal decoding.

It is not an approximation — it is a pure speedup, and this point is very often misunderstood.

The real-world speedup is about 1.5–3×, depending on the acceptance rate —

That is, how closely the draft model matches the main model. For predictable text (code, structured text) the acceptance rate is high, so the gain is large;

For creative text it is smaller. Variants without a separate draft model also exist, using n-grams from the prompt itself to propose tokens.

Prompt caching

system prompt2,000 tokensidentical on every request
RAG documents3,000 tokensidentical within a session
question50 tokensvaries

no cache: re-prefill 5,050 tokens every timewith cache: prefill only the 50 new tokens

BenefitMagnitude
Lower TTFTVery significant when the prefix is most of the prompt
Lower costMany providers bill cached tokens at a much lower price
Higher throughputThe GPU does not redo old work

A prompt design consequence — easy to miss

The cache only applies to an exactly identical leading part. So put everything stable first and everything that changes last: system prompt, then few-shot examples, then documents, and finally the user's question. Inserting a timestamp or request id at the start of the prompt wipes out the cache — a small ordering mistake that loses the entire benefit.

Throughput and latency are opposed

A larger batch raises throughput and degrades TPOT. No configuration is optimal for both, so pin down the requirements first: a chatbot needs TPOT under roughly 50ms so text streams faster than people read, while bulk jobs care only about throughput and can push the batch to the max. Answering "optimize both" is the wrong answer.

TechniqueSavingsNotes
1. Response cachingEqual to the duplicate rate — possibly 30–70%Cheapest and most profitable. Real questions repeat more than you think

The top two rows hold almost all the benefit

Response caching and difficulty-based routing usually save more than all model-layer optimizations combined — and both live at the application layer, without touching the GPU. Raising them before quantization and speculative decoding is the right order, because it shows you optimize for real cost, not for technical interest.

14

Common mistakes

Sizing VRAM by weights alone

At high batch the KV cache is often larger than the weights. Count both.

Using static batching

The whole batch is held by the longest request. Continuous batching gives several times more throughput.

Putting a timestamp at the start of the prompt

It wipes out the prefix cache. Stable things first, changing things last.

Trying to optimize both throughput and latency

They are opposed. Pin down the product requirements first.

Reporting only average latency

The average hides the tail. Report p95 and p99.

Optimizing the model before caching at the application layer

Response caching and model routing usually pay more than all GPU optimizations combined.
