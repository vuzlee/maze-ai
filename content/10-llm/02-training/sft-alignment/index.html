SFT & alignment

The most-asked boundary: fine-tuning teaches behavior, RAG supplies knowledge —

Get this wrong and the whole project fails. This lesson goes from SFT and the trick of masking the loss on the prompt, to three-step RLHF, then to DPO —

How to drop the reward model entirely and still learn from comparison pairs.

01

Mental model

Pretraining makes the model know; fine-tuning and alignment teach it how to answer the way the asker wants.

Three layers in sequence: can write → can follow instructions → can pick the answer people prefer.

Pretrainingpredict the next token over trillions of tokens → knows language and facts, but can only continue text
SFTlearns from (request, sample response) pairs → can follow instructions instead of just continuing
Alignmentlearns from comparing two responses — RLHF (reward model + PPO, three steps) or DPO (one step)

A second axis, independent of the three layers above, is how many weights get updated:

full fine-tune100% of parameters
LoRA · adds two small matrices0.1–1% of parameters
QLoRA · LoRA on a 4-bit compressed model0.1–1% · runs on a single GPU

Remember one sentence

SFT teaches the model format and behavior; alignment teaches it preferences; and LoRA is only a resource-saving technique — it does not change whether you are doing SFT or DPO. Mixing up these three axes is the most common conceptual mistake when discussing fine-tuning.
02

Should you fine-tune

This is the question to answer first, and in most cases the answer is no.

Model needs to know internal information → RAGknowledge changes; fine-tuning would need retraining on every update
Need an exact output format → prompt + structured outputcheap, fixable immediately, no data needed
Need a fixed writing style → fine-tunestyle is hard to fully express in instructions
Need a smaller model for a narrow job → fine-tune + distillationa fine-tuned 7B model can beat a large model on a narrow task, at far lower cost
Need lower latency and cost → fine-tune to drop a long promptno need to send 2000 tokens of instructions on every call
Need high accuracy in a narrow domain → fine-tune, once RAG is exhaustedspecialist jargon, unusual formats that prompting cannot cover

The boundary to remember

Fine-tuning teaches behavior; it cannot reliably inject knowledge. The model may learn to talk about an event yet still get the details wrong, because training only shifts a distribution rather than creating an exact lookup. If the knowledge can change, use RAG. This is the most common wrong answer to "when should you fine-tune".

Order to try: a better prompt → few-shot → RAG → fine-tune.

Each step costs tens of times more than the previous one in effort and running cost, so go in order and only move up when the step below is exhausted.

03

SFT — supervised fine-tuning

Data: (request, sample response) pairs, written or curated by humans

Training objective: EXACTLY the same as pretraining — predict the next token.
The only difference: the data is dialogue, and the loss is computed ONLY on the response.

Chat template — a detail you must get right

Each model has its own format. Get it wrong and quality drops sharply
with no error reported:

<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
What is the capital of France?<|im_end|>
<|im_start|>assistant
Paris.<|im_end|>

→ always use tokenizer.apply_chat_template() instead of concatenating strings yourself.
learning rate — 1e-5…2e-5 full, 1e-4…3e-4 LoRALoRA tolerates much higher learning rates
epochs — 1–3beyond 3 it usually starts memorizing the data
effective batch size — 32–128use gradient accumulation if VRAM is limited
sequence length — enough for the longest sampletruncation cuts off the end of responses and teaches the model to stop in the wrong place
warmup — 3–5% of stepsavoids wrecking the weights in the first steps
04

Masking the loss on the prompt

system-100masked
user · question-100masked
assistant · answerreal tokensloss computed here

no loss-100 is the index PyTorch ignoresthe part the model must learn to generate

Why mask: if the loss also covers the prompt, the model is being taught to generate the user's question —

A pointless task that dilutes the learning signal. With long prompts and short responses, most of the gradient goes into memorizing the prompt.

When NOT masking is right

When you want the model to learn the distribution of the whole conversation, for example continued training on domain data so the model gets used to specialist terminology. Then learning the user's part is useful too. But for instruction-following SFT, masking is the correct default, and libraries like TRL already handle it through a config parameter.

In multi-turn dialogue, every assistant turn contributes to the loss, and every user turn is masked.

This implementation detail is often gotten wrong when writing your own data-preparation function.

05

RLHF — three steps

Step 1 · SFTtrain on sample responses → yields model π_ref, used as the reference point
Step 2 · Reward modelhumans label pairs (preferred response, rejected response) → train a scoring model r(x, y)
Step 3 · PPOoptimize the policy for high reward without drifting too far from π_ref
maxE[ r(x, y) ]high reward−β · KL( π ‖ π_ref )penalty pulling back to reference
reward model loss=−log σ( r(x, y_chosen) − r(x, y_rejected) )Bradley-Terry

Why the KL penalty is needed

Without it, the policy finds ways to exploit holes in the reward model — producing bizarre text that the reward model scores highly, known as reward hacking. The reward model is only an approximation of human preference, and every approximation has holes when optimized too hard. The KL penalty keeps the policy in the region where that approximation is still trustworthy.

Why RLHF is hard to deploy: it needs four models in memory at once —

The policy being trained, the reference model, the reward model, and PPO's value model.

On top of that, RL is inherently sensitive to hyperparameters and hard to reproduce.

That is the entire motivation for DPO.

06

DPO — dropping the reward model entirely

The "maximize reward under a KL constraint" problem has a closed-form solution — so the reward can be rewritten in terms of the policy itself, and the reward model disappears.

r(x, y)=β · log[ π(y|x) / π_ref(y|x) ]reward hidden in the policy+const
L=−log σ( β·log[π(y_chosen)/π_ref(y_chosen)] − β·log[π(y_rejected)/π_ref(y_rejected)] )plug into Bradley-Terry, only the policy remains

Raise the probability of the preferred response, lower the probability of the rejected one —

Both are measured relative to the reference model. That "relative" part plays the role of the KL penalty, so no separate term is needed.

The formula in words: raise the probability of the preferred response, lower the probability of the rejected one.

Both terms are measured relative to the reference model — so the KL penalty is already built into the formula.

RLHF (PPO)

Models in memory 4

Separate reward model yes

Loop RL — sample, score, update

Stability sensitive to hyperparameters

Data freshly generated during training (online)

Peak quality can be higher if done well

DPO

Models in memory 2 — policy and reference

Separate reward model no

Loop ordinary supervised learning

Stability much more stable

Data fixed

Peak quality nearly as good, much easier to reach

DPO's weakness

It learns from a fixed dataset, so it cannot explore the responses the current policy produces — whereas RLHF scores the very samples the policy just generated. As a result, DPO can drift if the preference data was generated by a very different model. Online DPO variants were created to fill exactly this gap.
07

Comparison of alignment methods

SFT — sample responses · 1 modelmandatory foundation before everything else
RLHF / PPO — comparison pairs · 4 modelsstrongest if done well; complex, expensive, hard to reproduce
DPO — comparison pairs · 2 modelstoday's practical default — simple, stable
ORPO — comparison pairs · 1 modelfolds in the SFT loss, no reference model needed
KTO — good/bad labels, no pairs needed · 2 modelsusable when you only have scattered likes/dislikes from users
RLAIF — comparison pairs judged by AI · 4 modelscheaper than hiring human raters; quality depends on the judge model

KTO is worth knowing for a practical reason

Real user feedback is almost always unpaired — one turn gets a dislike, another gets a like, and there are never two responses to the same question to compare. DPO needs pairs, so it cannot use this directly. KTO accepts exactly that kind of data, making it the natural choice when you have real product logs rather than paid annotations.
08

Data — quality over quantity

LIMA · 1,000 carefully curated examplesinstruction following: equal
tens of thousands of average-quality examplesinstruction following: equal

tens of times more datayet the same result

The explanation: the knowledge is already there from pretraining. SFT only teaches the model the format and style of responses — and that does not take much data.

Consistent formattingmodels pick up surface patterns very fast — messy formatting teaches messiness
No wrong responsesone wrong example does more harm than ten correct ones can undo — the model cannot tell which is right
Diverse request types1000 examples of one kind teach only that one kind
Sensible response lengthall-long responses teach the model to always write long, even when the question needs one word
Include refusal examplesevery example answerable → the model learns it must always have an answer — the root of making things up

The last row is the most often overlooked

If the SFT data only contains questions the model can answer, you are teaching it that there must always be an answer. If you want the model to say "I don't know" or "this information is not in the documents", the training data must contain such examples. This is also a direct link to RAG systems, where refusing when there is no evidence is the desired behavior.
09

Evaluating the model after fine-tuning

Held-out lossmeasures distribution fit · does not correlate well with perceived quality
Task benchmarksmeasure accuracy · only usable if the task has a clear right answer
Human-judged win ratedirect comparison with the base model · most reliable, but slow and expensive
LLM as judgeapproximates win rate · biased toward long responses and responses in its own style
Regression test suitechecks whether any capability was lost · mandatory, and the easiest to skip

On using an LLM as judge

It is fast and cheap, so using it is almost unavoidable, but you must know its two biases: it prefers longer responses, and it prefers a style like its own. Mitigations: swap the order of the two responses and judge twice, use a rubric with concrete criteria instead of "which is better", and always verify a small sample with real humans.
10

Common mistakes

None of these five mistakes raises any error — the model still finishes training, it just gets worse.

Fine-tuning to inject knowledge

The model learns to talk about the topic but still gets details wrong. If the knowledge can change, use RAG.

Wrong chat template

Quality drops sharply with no error. Use apply_chat_template.

Not masking the loss on the prompt

The model learns to generate the user's question; the learning signal gets diluted.

No refusal examples in the data

Teaches the model there must always be an answer — the root of making things up.

No regression test suite

You cannot detect that the model just lost an old capability.
