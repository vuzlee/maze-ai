RAG end-to-end

The answer "I used LangChain with a vector DB" says nothing.

This lesson walks the whole pipeline — chunking, embedding, index, hybrid search, reranking, context building, generation —

And most importantly: a decision tree for debugging when the system answers wrong, plus evaluation split into two layers.

01

Mental model

RAG does not teach the model new knowledge — it finds the right piece of a document and puts it into the question before the model answers.

RAG is two systems joined together: a search system runs first, a text generator runs after.

One sentence to remember

RAG is two systems joined together: a search system and a text generator. When it answers wrong, the first job is to find which layer failed — because the fixes are completely different. This is also what separates an answer from experience from an answer from the docs.
02

RAG or stuff it all into a long context

With models that take a 200k-token context, the fair question is: why still need RAG?

RAG

Cost per question pay for only a few thousand tokens

Latency low — short prompt

Data scale unlimited

Source citation natural — you know which chunk was used

With few documents can miss things if retrieval is weak

Data updates re-embed only what changed

Long context

Cost per question pay for the whole context, on every call

Latency high — prefill scales with length

Data scale hard-capped by the context window

Source citation hard to tell what the model relied on

With few documents more accurate — no step can miss anything

Data updates nothing needed

The practical verdict

Few, fixed documents — under a few tens of thousands of tokens, say one contract or one product manual — then putting everything into the context is simpler and more accurate. A large or constantly changing corpus leaves RAG as the only option. And the common approach today is to combine them: use RAG to narrow down to 20–50 chunks and then put all of them into a long context, instead of only 3–5 chunks as before.
03

Ingestion — the step that sets the quality ceiling

Parse documents — PDF, Word, HTML, tables, scansmulti-column PDFs get read out of order; tables turn into meaningless strings of numbers
Keep structure — headings, sections, hierarchylose the heading and the passage loses its context; you no longer know which product it is about
Attach metadata — source, date, author, access rightswithout metadata you cannot filter by time or by permission
Clean — strip headers, footers, page numbers, menusrepeated strings add noise to every chunk's embedding
Deduplicate — the same content in many filestop-k gets taken over by five copies of the same passage

The most underrated and most expensive step

No retrieval technique can save a passage that was misread from a PDF. Ingestion quality is the ceiling of the whole system. In real projects this is usually the part that takes the most time — and saying so in an interview is a clear sign of someone who has built real RAG rather than run a demo.

One technique worth knowing: prepend headings to every chunk. The passage "The warranty period is 24 months" does not say which product the warranty covers.

Add the heading path — "Product X > Policy >

Warranty" — to the start of the chunk and both the embedding and the LLM get the context.

04

Chunking

Fixed size — cut every N tokens, with overlapunstructured text; the simplest
By paragraph / sentence — cut at natural boundarieswell-written text
By structure — cut at headings, sections, table rowstechnical docs, regulations — usually the best
Semantic — cut where the embedding shifts sharplysounds nice but is costly and rarely beats structure-based cuts clearly
Multi-level — embed small pieces to search, return large ones to readwhen you need both search precision and full context
Small chunks · 100–200 tokens

Focused embeddings, more precise search — but context is lost, and the answer can get cut in two.

Large chunks · 800–1500 tokens

Keep full context — but one vector has to stand for many ideas so the embedding gets diluted, and the LLM's context is spent on irrelevant parts.

common range300–600 tokens, overlap 10–20%

Why overlap is needed

So the answer is not cut across a chunk boundary. If the needed information spans two sentences and the cut lands right between them, no chunk holds all of it and the system is bound to answer wrong — even with a perfect embedding and index. This is the subtlest failure mode in RAG, and the lab below shows it happening.

The multi-level technique is worth knowing because it breaks the trade-off above:

Embed sentences or small passages for precise search, but when a small passage is picked, return the whole larger section containing it for the LLM to read.

Precise when searching, full context when reading.

06

Embedding

An embedding turns a passage into a vector so that similar meanings give nearby vectors.

cos(a, b)similarity = (a·b)dot product / (|a|·|b|)two lengths

If the vectors are normalized to length 1, the denominator is 1, so cosine is exactly the dot product — much faster. Most vector DBs assume this.

Choosing an embedding modelcheck that it handles your language well — many models are strong only in English
Dimensions — 384 to 1536more dimensions are slightly more accurate but cost memory and run slower
Asymmetric prefixessome models require "query: " before the question and "passage: " before the passage
Maximum lengthpast the limit the tail is cut off silently — a chunk larger than the limit loses data
Changing the embedding modelyou must re-embed the whole corpus: vectors from two models cannot be compared

Two silent traps

Forgetting the prefix. With a model that requires asymmetric prefixes, leaving them out raises no error — it just drops retrieval quality noticeably with no sign at all.

Chunks longer than the model limit. The excess is cut and never embedded.

The passage exists in the corpus, but its ending is invisible to search.

07

Vector index

Flat — compare against every vector100% recall, memory equal to all the vectors · under ~100k vectors, and usually enough
HNSW — multi-layer graph, walk to nearby neighborsvery high recall, high memory since the graph is stored too · default at medium scale
IVF — partition into clusters, search only the few nearesttunable recall, medium memory · many millions of vectors
IVF-PQ — IVF plus vector compressionlower recall, very low memory · hundreds of millions of vectors, RAM-bound

The key point about choosing an index

Under roughly 100k chunks, use flat. Search is 100% exact, there are no hyperparameters to mistune, and latency stays under a few tens of milliseconds. A great many real RAG systems sit at this scale. Choosing HNSW or IVF before you need it adds a source of errors yourself — because they are approximate search, which means they sometimes miss exactly the chunk you need with no way of knowing.

For HNSW, two parameters matter: M (connections per node, affects memory and quality) and ef_search (candidates considered at search time —

this is the knob that trades recall for latency, adjustable at runtime without rebuilding the index).

08

Hybrid search

Vector search — catches meaning

"how do I send something back" finds the passage on the returns process, even with no words in common.

BM25 — catches exact words

"error code E-4021", proper names, document numbers, rare terms — vector search can miss them entirely.

The two methods complement each other, and vector search's weakness is the part people tend to overlook:

It compresses a whole passage into one vector, so a specific error code is just a small detail that gets diluted.

BM25 matches that exact string.

score(d)fused score = Σi 1 / (k + ranki(d))summed over each ranking · k is usually 60

A chunk ranked 2nd by vector and 5th by BM25 scores 1/62 + 1/65 = 0.0315.

RRF uses only ranks, not raw scores — so there is no need to normalize two kinds of score onto one scale.

Why RRF is popular

Cosine scores lie between −1 and 1, while BM25 scores have no upper bound and depend on document length. Normalizing these two scales onto a common basis so they can be added has no clean solution. RRF sidesteps it by using only ranks — simple, no tuning needed, and experiments show it is very strong.
09

Reranking

Bi-encoder — used for retrieval

Embeds the question and the passage separately, compares them by cosine. Passages can be embedded ahead of time, so it can search millions of them — but the two sides never see each other.

Cross-encoder — used for reranking

Feeds both in at once: [question] [SEP] [passage], with attention running across every word. Far more accurate — but the model must run on each pair.

Bi-encoder → top-50fast, high recall, scans the whole corpus
Cross-encoder → top-5slow, but only has to score 50 pairs
LLMreads 5 chunks already in the right order

Why reranking is the most profitable upgrade

By common experience, adding a reranker improves RAG quality more than almost any other tweak — more than switching the embedding model or adjusting chunks. The reason is that a bi-encoder must compress the passage into a vector before it knows the question, while a cross-encoder sees both at once. The cost is only a few tens of milliseconds of extra latency for 50 pairs.
10

Building the context

Number of chunks — 3–10 after rerankmore usually dilutes rather than helps
Orderput the most relevant chunks first or last, not in the middle
Include metadatasource, date, section heading — so the LLM can cite and knows which is newer
Number the chunksso the LLM can refer to them by number when citing
Token budgetfixed hard; drop the lowest-ranked chunks rather than cutting one in the middle

Lost in the middle

Experiments show LLMs pay the least attention to the middle of a long context — information at the start and end is used noticeably better. The direct consequence: after reranking, don't mechanically order chunks by descending score. Putting the best chunk first and the second best last is a simple trick with a measurable effect.

On processing the question before retrieval, two techniques are worth knowing:

Query rewriting for multi-turn chat — "what about the other one?" retrieves nothing unless it is rewritten into a full question;

And generating multiple queries from one question then fusing the results, useful when the question has several facets.

Generation and citation

You are an assistant that answers from the provided documents.

RULES:
- Use only information in the passages below.
- Cite the passage number for every claim, as [1], [2].
- If the passages do NOT contain enough information, say so
  clearly and do not guess.

PASSAGE 1 (source: policy-2026.pdf, section Warranty):
...

QUESTION: ...
Require citationsusers can verify, and having to cite in itself reduces fabrication
Allow refusalwithout this way out the model is forced to make things up when there is no evidence
State source and datewhen two chunks conflict, the model knows which is newer
Say so when information conflictsbetter than picking a side at random

Allowing refusal is the single most effective change

If the prompt does not say clearly that "not found" is a valid answer, the model will always try to build an answer from whatever is in the context — even when the chunks are completely unrelated. This is the biggest source of fabrication in RAG systems, and it ties directly to the point in the fine-tuning lesson: training data also needs refusal examples.
12

Evaluation — the two layers must be split

Without splitting the two layers you cannot debug — because the fixes are completely different.

Retrieval layer — did it fetch the right chunk?

recall@k is the answer chunk in the top-k · MRR what rank it got. Needs a golden dataset: questions plus which chunk holds the answer.

Generation layer — did it use that chunk correctly?

faithfulness is the answer supported by the chunks or made up · relevance does it address the question · citation does it cite the right chunk.

How to build the golden dataset — the hardest part, and unavoidable:

  • Take real questions from user logs, don't invent them. Invented questions are always easier than real ones.
  • For each one, a human marks which chunk holds the answer. 50–200 questions are enough to catch most problems.
  • Keep questions that have no answer in the corpus too — to test whether the system knows how to refuse.

Why recall@k is the most important metric

Because it is the ceiling of the whole system: if the right chunk is not in the context, no LLM, however good, can answer correctly. So when improving RAG, I always measure recall@k first — if it sits at 60%, all the effort spent tuning prompts is pointless next to fixing the retrieval layer.
13

Debug tree — when RAG answers wrong

Go top to bottom and stop at the first question that answers "no" — that is exactly where it broke.

1 · Is that information in the corpus?no → a data problem, not a RAG problem. Add documents.
2 · Is the answer passage still whole after chunking?no → chunking split the information. Raise overlap, cut by structure.
3 · Does retrieval fetch that chunk? (measure recall@k)no → try hybrid search if the question has codes or proper names · check the embedding model's prefixes · check whether the approximate index misses it · add a reranker
4 · Is that chunk in the context sent to the LLM?no → cut by the token budget, or ranked outside the top-k. Raise k.
5 · Does the LLM use that chunk?no → the chunk sits mid-context, reorder · the prompt is not clear enough about relying on the documents · the model is too weak
Used but still wrongtwo chunks conflict, or the document itself is wrong

Debugging a RAG system that answers wrong

When a RAG system answers wrong, follow exactly the five ordered steps above instead of guessing along the lines of "tweak the prompt, then swap the vector DB". Each step rules out one layer, so by the end you know for sure where the bug is.
14

Common mistakes

No evaluation set

Every change is a guess. 50 real questions with their correct chunks are enough to start.

Chunks without overlap

The answer is cut across a boundary and no chunk holds all of it.

Vector search only

Misses error codes, proper names, document numbers. Add BM25 and fuse with RRF.

Not letting the model refuse

It is forced to make things up when the context lacks the answer.

Putting the best chunk mid-context

Lost in the middle — the model pays the least attention there.

Changing embedding model without re-embedding

Vectors from two models cannot be compared. Results become random.
